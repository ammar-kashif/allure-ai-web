**Gathered:** 2026-03-12

<domain>
## Phase Boundary

Build the Python FastAPI backend with audio upload, Moonshine Voice transcription with speaker diarization, and transcript retrieval endpoints. The backend runs at localhost:8000 and serves the Next.js frontend via proxy routes already built in Phase 1. API contracts must match the existing frontend proxy calls (`POST /recordings`, `GET /recordings/{id}/status`, `GET /recordings/{id}/transcript`).

</domain>

<decisions>
## Implementation Decisions

### STT Engine
- Moonshine Voice Base model — balance of speed and accuracy
- Target: 5-minute recording processed in under 30 seconds on M3
- Target: 30-minute recording processed in under 2-3 minutes on M3
- Accept multiple audio formats: webm (from browser recorder), mp3, wav, m4a (from Zoom/Teams uploads)
- Audio input will be online meeting recordings (primary) and clean laptop mic recordings (secondary)

### Speaker Diarization
- Auto-detect number of speakers — no user input required
- Reuse the diarization methodology from the existing allure-ai repo (github.com/ZainAbbas97/allure-ai) which uses speech engine approach
- Filter out speakers with <1% talk time to remove false detections and noise
- Expect 2-3 speakers typically, minimal overlapping speech
- Include speaker statistics in response: talk time percentage, utterance count per speaker

### Transcript Segment Granularity
- Utterance-level segments — one segment per continuous speaker turn (until speaker change or long pause)
- Merge consecutive segments from the same speaker into one segment for cleaner output
- Segment-level timestamps only (start_time, end_time per segment) — no word-level timestamps
- Include confidence score per segment from STT engine

### Processing Model
- Async processing with job queue — upload returns immediately with job ID
- Sequential processing: one recording at a time (queue-based, predictable M3 memory usage)
- Status endpoint returns state transitions only: pending → processing → completed → failed
- No progress percentage — just state changes (matches existing frontend polling pattern)

### API Contract Alignment
- Frontend proxy routes already call: `POST /recordings`, `GET /recordings/{id}/status`, `GET /recordings/{id}/transcript`
- Roadmap listed `/api/transcribe` and `/api/transcripts/{id}` but backend must match the existing frontend code
- Status values: pending, processing, completed, failed (frontend maps these via existing statusMap)

### Claude's Discretion
- Audio format conversion pipeline (ffmpeg or similar for webm → wav preprocessing)
- Job queue implementation (in-memory queue, asyncio task, or lightweight task runner)
- Moonshine model loading and caching strategy
- Audio file storage path and cleanup policy
- Error response format and error codes
- Health check endpoint design
- CORS configuration details

</decisions>

<specifics>
## Specific Ideas

- Reuse diarization approach from github.com/ZainAbbas97/allure-ai — tested and works well for the team's use case
- Filter speakers with <1% talk time to get accurate speaker count without manual input
- Online meeting audio is the primary input type — optimize for that quality level

<code_context>
## Existing Code Insights

### Reusable Assets
- Existing allure-ai Python repo (github.com/ZainAbbas97/allure-ai) — has working STT and diarization pipeline to reference/port
- Frontend proxy routes already built at `src/app/api/recordings/` — defines the API contract the backend must match

### Established Patterns
- Frontend status mapping in `src/app/api/recordings/[id]/status/route.ts`: pending/processing → "processing", completed/ready → "ready", failed/error → "error"
- Frontend expects `backendData.id` from POST response to use as backendId for subsequent status/transcript calls
- Audio uploaded as multipart/form-data with `file` field

### Integration Points
- `POST /recordings` — frontend sends multipart form with audio file, expects `{ id: "..." }` response
- `GET /recordings/{id}/status` — frontend expects `{ status: "pending"|"processing"|"completed"|"failed" }`
- `GET /recordings/{id}/transcript` — frontend expects transcript JSON (format TBD by researcher/planner based on decisions above)
- Frontend SQLite stores `backend_id` linking local recording to backend job
- Audio files stored locally at `public/recordings/{id}.webm` on frontend side
