# Phase 02.1: UI/UX Overhaul - Modern SaaS Dashboard - Research

**Researched:** 2026-03-13
**Domain:** Frontend UI/UX redesign (shadcn/ui, Tailwind CSS v4, Next.js 16)
**Confidence:** HIGH

## Summary

This phase transforms the existing functional but plain UI into a polished SaaS dashboard. The codebase already uses shadcn/ui (base-nova style), Tailwind CSS v4 with oklch color variables, and Next.js 16 with App Router. The existing `globals.css` already has sidebar-specific CSS variables (sidebar, sidebar-foreground, etc.) but they are set to neutral grays -- they need indigo values. The current layout uses a simple top header bar that will be replaced with a collapsible sidebar.

The shadcn sidebar component (`npx shadcn@latest add sidebar`) provides a complete collapsible sidebar solution with `SidebarProvider`, `Sidebar`, `SidebarInset`, and an "icon" collapsible mode that matches the desired collapsed-to-rail behavior. Fonts need switching from Geist Sans/Mono to Space Grotesk (headings) + Inter (body) via `next/font/google`. The dashboard home page (`src/app/(dashboard)/page.tsx`) is currently a simple welcome screen that needs to become a stats + recent activity dashboard.

**Primary recommendation:** Use the shadcn sidebar component with `collapsible="icon"` mode, update CSS variables to indigo theme in one pass, add Space Grotesk + Inter fonts via next/font, then progressively polish each existing view.

### Anti-Patterns to Avoid
- **Hardcoded color values instead of CSS variables:** Use `bg-primary`, `text-primary` etc. -- never hardcode `#4F46E5` in component classes
- **Overriding shadcn component internals:** Modify through CSS variables and className props, not by editing `sidebar.tsx` source
- **Creating new layout wrappers when SidebarInset exists:** The shadcn sidebar already provides `SidebarInset` for the main content area
- **Using `font-heading` on body text:** Space Grotesk is only for headings (h1-h4, brand text). Body stays `font-sans` (Inter)

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Collapsible sidebar | Custom sidebar with state management | shadcn sidebar component | Handles collapse animation, mobile sheet, keyboard shortcuts, cookies persistence |
| Sidebar mobile responsive | Custom drawer/sheet | shadcn sidebar mobile mode | Built-in sheet on mobile, sidebar on desktop |
| Stat cards | Custom div layouts | shadcn Card component | Consistent borders, shadows, padding |
| Search input | Styled raw input | shadcn Input component | Consistent focus ring, border styling |
| Font optimization | Google Fonts CDN link tags | next/font/google | Zero layout shift, self-hosted, font subsetting |
| Theme variables | Tailwind config colors | CSS custom properties in globals.css | Already established pattern, works with shadcn |

**Key insight:** This phase is about theming and layout restructuring, not new functionality. Every visual change should flow through CSS variables and existing shadcn component APIs to avoid diverging from the established component system.

## Common Pitfalls

### Pitfall 1: SidebarProvider Must Wrap Both Sidebar and Content
**What goes wrong:** Sidebar collapse/expand state doesn't propagate; triggers don't work
**Why it happens:** SidebarProvider placed too low in the tree, or Sidebar and main content are siblings outside the provider
**How to avoid:** Place SidebarProvider at the dashboard layout level, wrapping both AppSidebar and SidebarInset
**Warning signs:** `useSidebar` hook throws "must be used within SidebarProvider"

### Pitfall 2: Font Variable Not Propagating
**What goes wrong:** Space Grotesk doesn't render; falls back to system font
**Why it happens:** CSS variable `--font-heading` defined on body but Tailwind theme doesn't reference it, or the font family name doesn't match
**How to avoid:** Ensure `@theme inline` in globals.css maps `--font-heading` to the CSS variable. Verify with browser DevTools > Computed Styles > font-family
**Warning signs:** Headings look identical to body text

### Pitfall 3: oklch Values Out of Gamut
**What goes wrong:** Colors render differently across browsers or appear washed out
**Why it happens:** oklch chroma values too high for sRGB displays; browsers clamp differently
**How to avoid:** Keep chroma at or below 0.22 for indigo hues. Test in Chrome and Safari. The existing theme already uses oklch so the pipeline is proven
**Warning signs:** Colors look different in Chrome vs Safari

### Pitfall 4: Sidebar Width Pushes Content Off-Screen on Small Viewports
**What goes wrong:** Content area becomes too narrow when sidebar is expanded
**Why it happens:** Default sidebar width (16rem) plus content padding exceeds viewport
**How to avoid:** shadcn sidebar handles this with mobile sheet mode automatically. Ensure `SidebarInset` is used (it applies proper margin/width calculations)
**Warning signs:** Content wrapping or horizontal scroll on tablet-sized screens

### Pitfall 5: Tailwind v4 `@theme` vs `@theme inline`
**What goes wrong:** Custom CSS variables not available as Tailwind utilities
**Why it happens:** In Tailwind v4, `@theme` creates a separate layer; `@theme inline` makes variables available inline. The existing globals.css uses `@theme inline`
**How to avoid:** Add new font variables inside the existing `@theme inline` block
**Warning signs:** `font-heading` class doesn't work; Tailwind purges it

### Pitfall 6: Recording FAB z-index Conflicts with Sidebar
**What goes wrong:** FAB hidden behind sidebar overlay on mobile, or sidebar trigger overlaps FAB
**Why it happens:** z-index stacking context conflicts between fixed-position FAB and sidebar
**How to avoid:** FAB is already `z-50`. Sidebar uses its own stacking. Test mobile sheet mode explicitly to verify FAB remains accessible
**Warning signs:** FAB disappears when sidebar sheet opens on mobile

### Search Input with Debounce
```typescript
// Pattern for Recording Hub search
import { useState, useDeferredValue } from "react"
import { Input } from "@/components/ui/input"
import { Search } from "lucide-react"

function useSearchFilter(recordings: Recording[]) {
  const [query, setQuery] = useState("")
  const deferredQuery = useDeferredValue(query)

  const filtered = deferredQuery
    ? recordings.filter((r) =>
        r.title.toLowerCase().includes(deferredQuery.toLowerCase())
      )
    : recordings

  return { query, setQuery, filtered }
}
```

## Open Questions

1. **Dashboard stats API endpoint**
   - What we know: `useRecordings()` hook exists and returns all recordings. Outcomes are fetched per-recording.
   - What's unclear: Whether to aggregate stats client-side (iterate recordings) or create a dedicated `/api/stats` endpoint
   - Recommendation: Client-side aggregation from existing hooks for v1 (simpler, no backend changes). Recording count is trivial; outcomes count requires summing across recordings which may need a lightweight query.

2. **Sidebar collapse state persistence**
   - What we know: shadcn sidebar supports cookie-based persistence via `defaultOpen` prop on SidebarProvider
   - What's unclear: Whether cookie persistence is desired or if default-expanded is fine
   - Recommendation: Default expanded, let shadcn handle cookie persistence automatically (it does by default)

3. **"Tasks Created" stat when task management doesn't exist yet**
   - What we know: Tasks (Phase 3) doesn't exist. Promoted outcomes create tasks/requirements but there's no task list yet.
   - What's unclear: What number to show
   - Recommendation: Count promoted outcomes as "Tasks Created" for now. The promote endpoint already tracks this.
